# 10. 데이터 검증·로딩·캐시 수명 계약

우선순위 P0(검증)/P1(로딩 개선) / 상태 구현 반영·잔여 검증 있음 / 선행 01 / 규모 중

## 현재 근거

`PGDataTableManager.h/.cpp`에는 지연 로딩, LRU, 타입 매핑, SearchKey 인덱스가 있다. LoadDataTable은 TryLoad를 사용하고 GetRowData는 행 포인터를 반환한다. 캐시에서 테이블을 제거하는 API도 있어 장기 보관 포인터 사용처는 감사가 필요하다. 이는 현재 확정된 크래시라는 뜻은 아니다.

`FindSearchKeyProperty`에는 native SearchKey 매핑도 있으므로 신규 행은 메타데이터만 추가하면 된다는 개요 설명이 충분하지 않다. `PGStageManager::SpawnSingleEnemy`, `PGAbilityPlayerSkill`, `PGDamageFloaterManager::CreateFloaterWidget`에는 동기 로딩 경로가 있다.

## 최소 작업

1. 첫 단계는 테이블 ID 중복·누락 참조·음수/0 금지 값·스폰 배치 크기·보상 빈 후보·스킬 연계 순환을 검사한다. 테이블/행/필드/오류 이유를 출력한다.
2. 데이터 등록 목록과 native SearchKey 매핑의 누락을 검사하고, 동일 타입의 여러 테이블을 허용할지 명시한다. 첫 버전은 모호한 매핑을 오류로 처리한다.
3. 소비자는 행을 짧게 참조하거나 필요한 값을 복사한다. 장기 참조가 필요한 데이터는 소유권/핀 유지 방식을 정하고 캐시 제거 뒤 재조회한다.
4. 스테이지 시작 전 필요한 적·몽타주·UI·투사체 에셋을 준비한다. 전투 입력 순간의 동기 로딩을 줄이고 로딩 실패는 진행 가능한 오류 상태로 전달한다.
5. 에디터 검사와 패키지 런타임 검색을 둘 다 검증한다. 실제 AssetRegistry/Cook 포함 결과로 판단하며 SoftObjectPath 존재만으로 포함을 가정하지 않는다.

소유: PGData는 데이터 정의/조회, 에디터 전용 검증은 Runtime 의존성을 늘리지 않는 별도 도구 경로, UPlayground는 구간 진입 조율. 전역 static Get 접근은 12에서 수명·월드 경계와 함께 다룬다.

## 수용 기준

- 잘못된 ID/중복 키/배치 0/누락 에셋 샘플에서 실행 전 구체적인 오류가 나온다.
- 새 행 타입 추가 시 등록 누락이 자동 검출되며 패키지에서도 같은 ID를 조회한다.
- 캐시 정리·GC 후 재조회/활성 스킬 동작이 안전하다.
- 준비 완료 후 대표 구간 첫 공격·첫 피격·첫 드랍의 로드 지연을 기록하고 제거 대상 경로를 확인한다.

디버그: 로드 시간·캐시 hit/miss·보유 테이블/메모리 추정치. 후순위: 대규모 외부 편집 툴; 먼저 검증 가능한 작은 에디터 도구를 만든다.

## 2026-09-19 구현 반영

스테이지 데이터 정적 검사, SearchKey/행 타입 중복 차단, 런타임 데이터 검색 키, 시작 전 적 클래스 검증, 일부 비동기 콜백 약한 참조, 에셋 검사/이관 Python 도구를 반영했다. 전체 비동기 로딩 정책과 캐시 수명 개편은 후속 작업이다.

상세 변경·재현 절차·최종 검증 결과: [1·2단계 실행 보고서](Stage12_Implementation_Report.md). 위 현재 근거는 최초 분석 시점 기록이다.

## 3·4단계 추가 반영

파밍 카탈로그의 ID·옵션·가중치·로드아웃·쿨다운 검증, 시작 스킬 몽타주 보유, 카탈로그 생성/백업 이관/읽기 전용 검사 도구를 추가했다. HUD의 스킬 행 장기 포인터를 제거하고 현재 핸들러를 조회한다. 카탈로그 장비 4개·빌드 4개·스킬 37개 연결 검사와 실제 맵의 파밍/성장 경로를 통과했다. 전체 캐시·비동기 준비 정책은 여전히 후속 범위다. 근거는 [3·4단계 실행 보고서](Stage34_Implementation_Report.md)를 따른다.
